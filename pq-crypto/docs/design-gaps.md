# Native Agave design gaps

This document covers the actual Agave `--experimental-pq-config` path. It remains an experimental implementation. [Implementation and ordering](native-overlap-main24-to30.md), [functional validation](../results/optimized-native-agave/validation-release30/native-overlap-and-parallel-auth/README.md), and [R30 measured results](../results/optimized-native-agave/profiling/pilot-r-main30-accepted-hour/README.md) describe separate kinds of evidence.

1. **Independent security assurance and interoperable profiles.** The private RFC8032 seed relation, hiding STARK parameters, quantum knowledge soundness, Falcon implementations, Ax target-sum WOTS profile, Quantumglow safety/liveness, and Falcon/ML-KEM TLS profile need independent cryptographic, side-channel and protocol review. Implementation tests do not establish those security claims. Publish interoperable vectors, negotiated wire versions and production signing APIs. Bind a governed native execution ABI/rules version or build commitment: common genesis and roles alone do not establish common execution code.

2. **Activation on an existing chain.** The experiments start from fresh native genesis, exercise classical transactions and enrollment before the Bank cutoff, and continue under Falcon policies afterward. Importing an existing classical ledger and rolling validator activation remain unimplemented. Specify a PQ-certified checkpoint, activation slot, historical commitments, validator-role migration, replay compatibility and rollback procedure. Classical snapshot hashes cannot authorize the new checkpoint. Explicitly decide whether pre-break same-address classical consent is allowed; the implementation supports that additional path alongside original-seed recovery.

3. **Committee lifecycle and authenticated time.** Membership, weights and leader windows are immutable for one finite Ax allocation, currently provisionable through 18,000 slots. Native stake/vote account changes do not update that committee. Implement consensus epoch rollover, stake changes, rewards, key rotation/revocation and history reclamation. Native Clock slots/epochs advance, but Unix timestamps can lag because ordinary vote timestamps/credits are absent. Time-based applications need a deterministic PQ-authenticated timestamp rule and versioned schedule; assigning each validator's local wall time would diverge state. [Observed runtime behavior](runtime-coverage.md).

4. **Rollback-resistant signing and recovery.** Ax allocations burn durably before signatures leave the signer. Restoring both a local monotonic file and its backup can still restore used signing state. Production requires independently protected monotonic state, fencing, HSM/service APIs, backup controls and recovery procedures. A larger finite allocation is neither anti-rollback protection nor automatic epoch management.

5. **Application migration and lifetime compatibility.** The rich onchain prelude covers unchanged authorities, System and program ownership, PDAs and `invoke_signed`, genuine SBF state/padding, CPI success and charged rollback, SPL custody, multisigner rotation and complete private-seed recovery. These are representative cases. Clock-based vesting/deadlines, live loader/program upgrades, multi-node ALT lifecycle, native staking economics, Token2022 extensions/confidential balances and application-embedded Ed25519/secp/BLS permits require further rules and end-to-end tests. AUTH-first conflicts with the standard AdvanceNonce-first lifetime layout. The load instruction carries a unique source/counter in its bytes; it does not exercise durable nonce accounts. Retiring a classical verification entrypoint does not recover its assets. [Coverage map](runtime-coverage.md).

6. **Execution, state and remaining serial work.** Bounded native Agave dependency waves run in parallel under native account locks, shared immutable account snapshots avoid whole-account copies per candidate, and certification promotes the exact executed Bank without a second SVM loop. Main25–30 remove redundant encoding, history scans and snapshots, overlap existing streams with journal persistence, and parallelize bounded receive authentication. One coordinator still orders consensus/admission/actions, encodes journal suffixes and waits for exact required ACKs. Ax reconciliation/signing, authoritative root ordering and parts of selection/repair/compaction remain serial. Starting authentication of the already collected batch before a journal wait is a possible further overlap and is not implemented. Canonical state-root construction still scans/sorts the visible account set despite cached leaves. Mainnet-sized state, long retention, snapshots and restart need separate validation. [COW and promotion](pq-cow-promotion.md).

7. **Admission, retention and proof resource budgets.** A successful send RPC currently acknowledges bounded queue admission, not durable inclusion. BlockhashNotFound can mean a future/unknown hash as well as expiry; the mempool has no complete acknowledged-ID expiry/cancellation contract. Specify certified hash history/last-valid-height handling, atomic queue/alias removal and a distinct terminal result before changing that behavior. The rejected Main27 hour retained 952 admitted IDs without an exact signed-wire/hash/parent-queue join; their cause is unproven. Journal/body limits provide experimental headroom rather than compact checkpoints or a production retention policy. Calibrate fees/CU and hostile peer, handshake, evidence and state-growth budgets. The existing 65,536-entry positive Falcon math cache still follows fresh transaction-specific policy checks; Main30 adds a separate one-entry canonical parse cache. Warm onchain Verify executes the proof in the native runtime; public-parameter prewarming is separate from verification and does not cache acceptance. Cold setup, offchain proving and temporary memory remain substantial and need independent budgets. Fresh R30 Verify executes in 38.610–39.494 ms across the eight warm native Bank calls, charging 1,006,151 CU and 1,008,161 transaction cost. RPC-observed finality is 0.706942992 s and the proof lifecycle is 111.614655975 s. These are separate scopes; isolated cryptographic CPU is unmeasured. [Actual proof evidence](../results/optimized-native-agave/profiling/pilot-r-main30-accepted-hour/README.md#warm-on-chain-proof-verification).

8. **Transport, client and streaming interoperability.** The experimental profile uses fixed peers/roles rather than the ordinary production gossip/Turbine pipeline. Specify negotiation, rekey/revocation, upgrade and wallet/hardware-signing APIs. Version-one candidate identity commits the complete payload: selection/native execution must close it before the first signed DATA. Subsequent production/publication can overlap, but true within-block prefix streaming needs a version-two identity, prefix durability, terminal completeness and recovery rules. Exact 48-byte replay identities and 64-byte RPC archive identifiers are retained. Broader transaction formats and signer-order permutations still need interoperability coverage.

9. **Operational and durable workflow recovery.** Exact finalized RPC receipts and balances are exercised; admin identity changes, notifications, snapshots and wider tooling remain incomplete. Specify readiness during certified-parent repair, long catch-up and archive publication: certified shared-Bank promotion can precede receipt archive completion. Migration clients need durable per-step checkpoints, exact committed-intent discovery, replacement credentials and upload cleanup across every enrollment/sealing/rotation boundary. The specialized interruption resume is not general workflow recovery. Experiment owners survive frontend disconnects and preserve signer history, failures and bounded cleanup; that does not establish production recovery at arbitrary crash boundaries.

10. **Sustained, adversarial and comparative validation.** R30 fully accepted its matched and pressure shorts at 10,985.9625 and 12,918.8914 drain-inclusive TPS, and the predeclared 3,660-second, 8k/s-total hour at 7,996.5247 TPS. The [same-Main30 ordinary reference](../results/optimized-native-agave/profiling/ordinary-main30-vs-pq-r30/README.md) fully accepted 9.6 million successful transactions over 600 seconds of traffic, at 15,995.0415 TPS including drain. PQ load acceptance combines every-ID source-finalized observations with all-eight native counts and full state/fee/balance oracles, rather than exhaustive all-eight status vectors for every load ID; the 607-transaction prelude has those complete archives. The ordinary audit checked all 9.6 million source signatures on all eight replicas. Keep accepted shorts, accepted hours and rejected attempts separate. A ten-minute ordinary run with the same modified binary, native default caps and classical signatures is a useful reference; it is not untouched production, a hardware ceiling or isolated cryptographic overhead. The configured matched/ordinary targets are 16k/s total, pressure is 32k/s, and the Main30 hour is 8k/s. The bounded PQ sources actually admitted 12,704.44/s matched and 14,481.11/s pressure over 120 seconds, and 7,998.68/s during the 3,660-second hour; ordinary met its 16k/s target over 600 seconds. These admission rates have a different denominator from drain-inclusive TPS. Longer runs, Byzantine equivocation, partitions, loss, leader failures, hostile future evidence, mainnet state and long-journal restart remain required. Thread CPU, coordinator active wall, nested stage timers, physical-host counters and transaction finality have different scopes. The literal `duplicate_execution_count=0` status field is not an instrumented execution census; same-Bank promotion is supported by source and regression controls.
