# Native runtime and application coverage

The modified validator executes actual Agave Bank, SVM and AccountsDB state. The tested migration cases establish specific authority and custody behavior. They do not establish compatibility with every existing Solana application, and there is a measured native Clock timestamp gap. This document separates local runtime tests from the eight-validator Rich-C client evidence and identifies the remaining application work.

## Native Clock observation and cause

Two read-only observations during the running Rich-C experiment queried finalized Clock on all eight validators, checked the genesis binding, and bracketed its slot with finalized `getSlot`. The 40-byte Clock was decoded as `slot:u64`, `epoch_start_timestamp:i64`, `epoch:u64`, `leader_schedule_epoch:u64`, `unix_timestamp:i64`, in little-endian order. A second observation fetched Clock, EpochSchedule and all eight native vote accounts together on every node. Raw account hashes and per-node wall/RPC brackets are in [the published observations](../results/continuous-agave/runtime-clock/manifest.json).

| Observation | All-eight Clock slot | Native epoch / leader-schedule epoch | Epoch-start timestamp | Onchain Unix timestamp | Wall minus Clock |
| --- | ---: | --- | ---: | ---: | --- |
| Slot-bracketed Clock | 5,656 | 7 / 8 | 1,791,800,912 | 1,791,801,389 | 2,131.89–2,133.84 seconds |
| Clock + epoch + native votes | 5,912 | 7 / 8 | 1,791,800,912 | 1,791,801,467 | 2,251.05–2,251.58 seconds |

The first observation's complete per-node RPC sequences took 1.52–1.95 seconds; Clock.slot lay within each finalized slot bracket. All eight nodes returned the same Clock values in both observations. The second query showed the actual native EpochSchedule: 432,000 normal slots, warmup enabled, first normal epoch 14 and first normal slot 524,256. Native epoch seven therefore starts at slot 4,064. PQ consensus independently remains in its finite Ax epoch one; these epoch numbers describe different mechanisms.

All 64 views of the eight native VoteStateV4 accounts had `last_timestamp = (slot:0, timestamp:0)`, no votes and no epoch-credit entries. Genesis initialization calls [`create_v4_account_with_authorized`](../../programs/vote/src/vote_state/mod.rs#L1359) with `Clock::default()`; the [native initializer](../../validator/src/bin/agave-pq-tool.rs#L988) creates those actual vote/stake accounts but the PQ consensus path does not submit stock vote timestamps or credits.

The native child Bank still runs [`update_clock`](../../runtime/src/bank.rs#L2817). Its [timestamp estimator](../../runtime/src/bank.rs#L3406) reads native vote timestamps and stake. [`calculate_stake_weighted_timestamp`](../../runtime/src/stake_weighted_timestamp.rs#L26) bounds the stale estimate against epoch-start time with a 25% fast bound. The persisted genesis uses the SDK's default 400 ms native slot duration. PQ's separately configured 500 ms cadence and actual processing delays do not update that native schedule. At slot 5,912, every observed Clock matches the resulting bound exactly:

```text
epoch_start + floor((5912 - 4064) * 0.400)
            - floor((5912 - 4064) * 0.100)
= 1791800912 + 739 - 184
= 1791801467
```

This is stale-vote correction, rather than a current wall-time estimate. If no stake-weighted estimate exists, the same Bank method retains the ancestor timestamp; slot-zero initialization uses genesis creation time. [`complete_bank`](../../core/src/experimental_pq.rs#L387) registers the required native ticks and freezes state. It does not call the Bank's timestamp-footer API or supply PQ-authenticated time. [Archived RPC block time](../../core/src/experimental_pq.rs#L2123) is taken directly from this native Clock.

The configured slot-based migration cutoff remains effective because Clock.slot and Bank.slot advance consistently. Unix-time vesting, deadlines, oracle freshness and other Clock-time predicates are not validated by the current workload: its [SBF counter instruction](../../runtime/tests/fixtures/pq-svm/workload.c#L27) reads no Clock and its vault uses explicit sequence numbers. A timestamp fix needs agreed PQ-authorized timestamp evidence or a certified temporal header, deterministic skew/monotonic/replay rules, and a governed execution version. Setting each node's local wall time would give different account roots. The running Main was left unchanged for these observations.

## Native stake and PQ committee are separate

The native service validates the onchain role-registry owner/bytes and native vote-account node identities [at activation startup](../../core/src/experimental_pq.rs#L942). It constructs each PQ validator's consensus weight from [`peer.stake`](../../core/src/experimental_pq.rs#L922) and builds the finite epoch's fixed leader schedule. [Registry encoding](../../core/src/experimental_pq.rs#L2440) includes each identity, vote address, configured weight and role keys; it does not list individual stake-account addresses. The independently pinned activation account root binds the complete initial native stake/vote state.

Subsequent [candidate execution](../../core/src/experimental_pq.rs#L401) runs ordinary Bank/SVM transactions and commits their complete state. It does not recompute the PQ committee from current native delegated stakes or credits. No native `is_role_account` guard or blanket configured Vote/Stake write rejection was found in this path. The [guard actually tested](../../runtime/src/pq_program.rs#L527) rejects writable CONFIG/ROLE_REGISTRY accounts in native PQ instructions; program ownership separately prevents unrelated programs from rewriting their data. Ordinary validator identity fee credits are native Bank economics, rather than changes to the registry's fixed consensus weights.

The local auxiliary Vote/Stake case proves the tested funds/authority operations, not a live configured-committee lifecycle. It does not demonstrate that native staking funds are stranded or that every configured-committee operation is permitted. Withdrawal/deactivation/authority changes may affect native economics while this finite epoch's PQ role keys, weights and scheduling remain static. Production must specify which stake state governs consensus, activation/deactivation and epoch boundaries, credits/rewards, native vote identity changes and governed role transitions, then test that mapping end to end.

## Application semantics still requiring migration rules and tests

| Remaining area | Current status and required work |
| --- | --- |
| Clock-based vesting, deadlines and time-dependent state | Measured stale Unix time is a functional gap. Agree on PQ-authorized native time and test actual Clock-reading programs before claiming compatibility. |
| Rent, native epochs, stake and rewards | Actual rent exemptions, policy rent growth, escrow rent/refunds and native warmup epoch advancement occur. Local native Vote/Stake withdraw/deactivate/withdraw-authority migration now passes; dynamic native voting, nonzero credits, cooldown maturity, economic rewards, epoch-bound application state, rent collection/underfunded-account behavior and consensus membership changes still lack a dedicated end-to-end correctness matrix. |
| Stock durable nonces | Mandatory AUTH-first prevents the SDK's AdvanceNonce-first nonce lifetime detection, explicitly reproduced in the funded-nonce test. That test proves ordinary recent-blockhash withdrawal, authority migration/change, advance and complete stored-fund/rent access; it does not grant durable-nonce lifetime. The SBF `source/counter` nonce also only creates unique recent-blockhash intents. Define a PQ nonce envelope and test the full expiration, durable execution rollback and fee contract. |
| Address lookup tables | The new local actual-program test covers create/extend/enrollment, resolved v0 transfer, one-slot warmup, full-width replay, deactivate/cooldown/close and authority/refund checks. Freezing, policy dependencies themselves loaded through tables, competing table operations, and multi-node v0 lifecycle remain outside that case. Historical [metadata-only v0 coverage](../../runtime/src/pq.rs#L2428) remains a separate regression. |
| Program loaders and upgrades | A local runtime test deploys real SBF through UpgradeableLoader and preserves visibility through private-parent detachment/live replay. Live upgrade-authority enrollment/rotation/revocation, upgrades during competing forks and archival ABI replay remain untested. The [native policy installer](../../runtime/src/pq_program.rs#L217) explicitly rejects executable authority accounts, so loader-v2 operations requiring the executable program address itself as signer need a separate supported migration rule. |
| Standard token breadth | Standard token transfer and local ATA/freeze/thaw work. Native SPL multisig account semantics, approve/revoke delegates, close authorities, mint-authority changes, wrapped SOL and the full cross-program authority graph need broader cases. The app's 2-of-2 vault is not an SPL multisig account. |
| Token2022 and confidential balances | Installing an ELF does not exercise its extensions. Transfer hooks, confidential ElGamal balances/proofs and other extension-specific authorities need application migrations. Native classical ElGamal proof entrypoints are retired after cutoff; that retirement does not recover confidential assets. |
| Custom classical permits and proofs | Native Ed/secp precompiles, secp recovery and classical ZK program entrypoints are gated. Custom SBF may implement its own classical signatures, pairing or permit logic. A Falcon transaction signer cannot rewrite those rules: upgrade or retire each affected authorization path and specify custody recovery. |
| Complete existing-chain authority graph | Representative same-address authority migrations preserve the tested assets. Production needs application-specific inventories, unsupported/off-curve/derived-seed handling, delegated/governance/bridge authorities, historical state migration and independently certified activation. The current results do not prove that every arbitrary account is recoverable or cannot become stranded. |

This audit changes documentation and collects public onchain data only. It does not alter the running validator, workload, genesis, execution rules or measured binary provenance.
